## Selected architecture and alternatives

Separate permanent geographic identity, temporary rendering allocation and
view-dependent submission. A pack provider produces immutable content and
representation rules. A common scheduler reserves capacity; workers prepare
bounded blocks; the allocator retains records; a selector builds draw-reference
lists; the renderer batches compatible prototypes and materials.

| Approach | Decision and reason |
|---|---|
| Smaller geographic units with the existing cell renderer | Adopt smaller units as a component; retaining a draw per unit would increase fanout |
| Repack every visible 32-byte record each frame | Reject the full-refresh design; 250,000 records are about 7.63 MiB before other uploads |
| Multi-draw around existing cell resources | Optional API optimisation; it does not remove underlying subdraws or geometry work |
| WebGPU or Three.js migration | Outside H's critical path; retain the native WebGL2 baseline |
| Small blocks, shared persistent records and compact draw references | Selected; supports independent residency, selection, batching and progressive replacement |

HR-02 selected 1 m detailed render blocks inside the existing 8 m logical cells
after measuring block sizes and bounded jobs with real workers. This is a local
generation choice; HR-03 has now verified GPU submission feasibility. Adjacent blocks
share a bounded worker job. Coarse
vegetation may use larger blocks. Retain the original parent sampling lattice,
candidate numbers and acceptance calculation; partition by parent root and
expand bounds for children crossing a storage boundary.

The implemented HR-03 WebGL2 backend stores each unchanged 32-byte record in
two RGBA32UI texels and uses four-byte slot references as instanced attributes.
A bounded RG32F phase/seed cache preserves the original normalized attribute
rounding and dither; integer-only UNORM decoding failed pixel parity during
exploration. Actual record uploads therefore cost 40 bytes per record. Fixed
record/cache/reference capacity is 24,236,480 bytes before shared prototypes
and concurrent resources. Both actual blade and large clump meshes have matched
native GPU measurements. See the HR-03 contracts and report for costs and scope. Relevant capabilities are documented
in the [WebGL2 specification](https://registry.khronos.org/webgl/specs/2.0.0/)
and [GLSL ES 3.00 specification](https://registry.khronos.org/OpenGL/specs/es/3.0/GLSL_ES_Specification_3.00.pdf).

A 500,000-record detail payload is about 15.26 MiB. Two 250,000-entry reference
lists are about 1.91 MiB. These are arithmetic payload illustrations, not a full
GPU-memory pass; include clumps, padding, capacity, metadata, prototypes,
textures, staging and all simultaneous allocations. Replace old per-cell GPU
storage rather than retaining a complete second detailed window.
